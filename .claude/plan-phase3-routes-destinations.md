## 1. 地図コンポーネントの選定調査

目的地登録（地図タップ）に必要。Web検索不可のため一般的な知識に基づく評価、不確実な点は「要検証」。

### 候補A: Leaflet + OpenStreetMapタイル（推奨）
- ビルドチェーンとの親和性: 良好。単体JS+CSSをCDN読み込みするだけで動作。既存の「ビルドチェーンなし・素のJS方針」に完全一致
- APIキー要否: 不要
- コスト: 基本無料（商用トラフィック規模でのOSM直接利用ポリシーは要検証、必要なら商用タイルプロバイダーへの切替を検討）

- APIキー必須、GCP課金アカウント登録が必要
- 無料枠はあるが超過時従量課金、クレジットカード登録がハードル

- Leafletに近いが導入・設定がやや複雑

**推奨（暫定）: 候補A Leaflet + OSM。** APIキー不要でLTA APIキーのみをサーバー側で管理するシンプルな構成を崩さず、ビルドチェーンなし方針に合致するため。**ただし商用トラフィックでのOSMタイル利用規約の最新状況は要検証**、本番リリース前に確認が必要。

## 2. 「関連のみ」フィルターの実ロジック設計

### 2-1. 目的地登録データの構造: バス停コード方式（推奨）

**地図タップ位置から最寄りバス停コード（`BusStopCode`）に変換して保存する。座標そのものの保存はしない。**

理由: 系統自動判別には最終的に「その地点を通るバス停」の特定が必要であり、登録時点で最寄りバス停に解決すれば以降の判定ロジックがシンプルになる。既存の`/api/bus-stops/nearby`（`limit=1`）をほぼそのまま流用できる。

**懸念点（要検討）**: タップ地点から最寄りバス停が利用者の意図とズレる可能性（単純距離判定で良いか、複数候補提示が必要か）。1目的地=1バス停コードか、周辺複数バス停を対象にするかも未確定。

**データ構造案（localStorage、キー `sgbusnavi_destinations`）**:
```json
[
  {
    "id": "uuid等",
    "busStopCode": "82009",
    "description": "Bukit Merah Int",
    "lat": 1.xxx,
    "lng": 103.xxx,
    "registeredAt": "ISO8601"
  }
]
```
CLAUDE.mdは「系統番号や地名検索の手動入力は不要」と明記のため、自由入力欄は設けない。

### 2-2. 「この系統が登録済み目的地を通るか」の判定に必要なデータ

**`BusRoutes`が必須。** `BusStops`単体や`BusServices`（起点・終点のみ）では「途中経由するか」を判定できない。フェーズ2の「行き先地名表示にBusServices/BusRoutes不要」という発見は地名表示に限った話であり、経路全体の判定には引き続きBusRoutesが必要。

判定ロジック（想定）:
1. 現在表示中のバス停で発着する系統一覧を`/api/bus-arrival`のレスポンス（`Services[].ServiceNo`）から得る
2. 各系統について、`BusRoutes`から`ServiceNo`＋`Direction`の一致するレコード群を取得し、`BusStopCode`列に登録済み目的地の`busStopCode`が含まれるか判定
3. 含まれていれば「関連あり」

**フェーズ3で新規にBusRoutes（全26,808件、54ページ）を取得・キャッシュする設計が必要。** BusStopsキャッシュ基盤と同一パターンを踏襲できる見込み。

**確定（2026-09-13実データ検証済み）**: `v3/BusArrival`に`Direction`フィールドは**存在しない**（`Services[]`/`NextBus*`いずれにも無し）。代替として`OriginCode`/`DestinationCode`が使えるが、**循環路線（後述、全体の約32%）ではOrigin=Destinationになり方向を区別できず機能しない**。よって「関連のみ」判定は、`BusRoutes`側で同一`ServiceNo`の**両`Direction`を調べ、いずれか一方でも現在地点と目的地の両方を含む`StopSequence`があれば関連あり**とする順序無視の緩い判定からスタートし、誤判定が問題になれば`OriginCode`一致による絞り込みを追加する段階的アプローチを採用する。

## 3. 経路モーダルの実データ化設計

### 3-1. BusRoutes（全26,808件）＋BusServices（全800件）の取得・キャッシュ方針

フェーズ2のBusStopsキャッシュ基盤（`fetchAllBusStopsFromLta`等）のパターンを踏襲。

**重要な訂正（2026-09-13実データ検証済み）**: 当初「BusServicesは不要」としていたが誤り。**BusServicesも取得・キャッシュ対象に含める**（循環路線判定の`LoopDesc`フィールドがBusRoutesには存在せずBusServices側にのみ存在するため）。BusServicesは全800件・2ページのみで負荷は軽微。

- BusRoutesページング: `$skip`方式、54ページ×250ms間隔＝約13.5秒。起動非ブロッキングの既存パターンで対応可能
- BusRoutesフィールド絞り込み: `ServiceNo`, `Direction`, `StopSequence`, `BusStopCode`で足りる（`Category`フィールドはBusRoutesには存在しないことを確認済み。`Distance`は経由地点順の裏付けに使える可能性があり保持を検討）
- BusServicesフィールド絞り込み: `ServiceNo`, `Direction`, `Category`, `OriginCode`, `DestinationCode`, `LoopDesc`
- メモリ・検索方式: `ServiceNo+Direction`をキーにしたMapへの事前グルーピング（`Map<"ServiceNo|Direction", Array<{StopSequence, BusStopCode}>>`）を、BusStopsの`busStopCodeToDescriptionMap`と同様のパターンで構築する。循環路線判定用に`ServiceNo+Direction`→`LoopDesc`のMapも別途構築する
- ファイルサイズ: 概算1.5〜2MB程度と推定（未実測、要検証）
- **`StopSequence`は欠番があることを確認済み（サンプル24系統・方向中3組=12.5%で欠番あり）。「配列インデックス=StopSequence」という前提を置いてはならず、昇順ソートキーとしてのみ扱うこと**

### 3-2. 主要経由地点選定ロジック（優先順位: 1.MRT駅・インターチェンジ 2.主要地名）

**優先順位1のヒューリスティック（実データ確認済みだが全件網羅性は未検証）**:
- インターチェンジ: 正規表現`/\bInt$/`（末尾が"Int"）
- MRT駅: 正規表現`/\bstn\b/i`（大文字小文字区別せず"stn"を含む）
- 要実データ検証: 上記2パターンで全国のMRT駅・インターチェンジを漏れなく拾えるか未検証。例外パターンの存在可能性あり

**優先順位2（主要地名リスト）**: CLAUDE.mdの例示は「Orchard、Chinatown等」。ハードコードリストの具体的な中身は未確定（要企画判断）。

**推奨アルゴリズム**:
1. 優先順位1（MRT駅・インターチェンジ）で経由地点候補を`StopSequence`順に抽出
2. 2〜3箇所に満たない場合のみ、優先順位2の主要地名リストで補完
3. まず優先順位1で候補を出し、不足時のみ2で補う方針とし、無理に水増ししない（0件なら始点・終点のみ表示）
4. 2〜3箇所を超えてマッチした場合の間引き方法は未確定（要検討）

### 3-2-補. 循環路線（Loop）への対応（新規追加、実データで存在確認済み）

BusServices全800件中257件（約32%）が`LoopDesc`非空＝循環路線であることを実データで確認した。`v3/BusArrival`で観測された「同一系統でOrigin=Destination」というケースも全件このパターンと一致した。**無視できない頻度のため専用対応が必須**。

- 循環路線（`LoopDesc`非空）の場合、経路モーダルの「区間（始点→終点）」表示が成立しない（始点=終点になるため）。代わりに「Loop via {LoopDesc}」のような専用表示にする
- 経由地点選定でも、循環の折返し地点（`LoopDesc`が示す道路）を優先候補に含めることを検討する
- 具体的な表示文言・UIは未確定（要検討）

### 3-3. ルート線図（SVG）の動的生成方針

CLAUDE.md要件は「バス停マーカーなしの簡易ルート線図」であり、実際の地理座標を正確に描画する必要はないと解釈できる。選定された始点・終点・経由地点N箇所を、SVGの固定`viewBox`内に機械的に配置する簡易ロジック（地理的位置関係を反映しない模式図）を推奨。実緯度経度を線形変換してマッピングする方式も選択肢だが、**どちらを採るかは未確定（要検討）**、前者の方が実装コストは低い。

## 4. 3機能の依存関係・優先順位、スコープ分割（決定）

```
[地図コンポーネント選定・導入] → [目的地登録] → [関連のみフィルター実ロジック]
                                                    （BusRoutes基盤も必要）

[経路モーダルの実データ化] （BusRoutes基盤のみに依存、目的地登録とは独立）
```

**スコープをフェーズ3-A / 3-Bに分割する。**

### フェーズ3-A（今回実施。地図ライブラリ不要、独立完結）
1. `v3/BusArrival`の`Direction`フィールド有無の実データ検証（最優先）
2. BusRoutes実データ疎通確認
3. BusRoutesマスタ取得・キャッシュ基盤の実装
4. MRT駅・インターチェンジ判定ヒューリスティックの全件検証
5. 経路モーダル用の経由地点選定ロジックの実装
6. 経路モーダルのSVG動的生成の実装

### フェーズ3-B（次回。地図コンポーネント選定確定後）
7. 地図コンポーネントの技術検証（OSMタイル利用規約確認、Leaflet組み込み・PWA/Service Workerとの共存確認）
8. 目的地登録機能の実装（地図タップ→最寄りバス停解決→localStorage保存）
9. 「関連のみ」フィルターの実絞り込みロジックの実装（3-Aで構築したBusRoutes基盤＋8の目的地データを利用）
10. 結合確認・実機検証

理由: 経路モーダルの実データ化は地図コンポーネント導入という重い作業を伴わず、BusRoutes基盤さえ整えば独立して価値を出せる。目的地登録は地図ライブラリ選定（要検証事項あり）とUX判断事項が多く意思決定コストが高いため分離する。

## 5. 受け入れ基準

### 5-A. 経路モーダルの実データ化（フェーズ3-A）

**正常系**: バスカードタップで実際のBusRoutesに基づく始点・終点が表示される。経由地点2〜3箇所がMRT駅・インターチェンジ優先で選定されラベル表示される。系統番号・区間タイトルは引き続き正しく表示される。

**失敗系**: BusRoutesキャッシュ未準備時はエラー落ちせず「経路情報を準備中です」等のフォールバック。該当`ServiceNo`+`Direction`がBusRoutesに存在しない場合は系統番号・区間タイトルのみのフォールバック。

**エッジケース**: 経由地点候補0件の系統は始点・終点のみ表示。同一`ServiceNo`で複数`Direction`存在時に現在のバスカードの方向を正しく特定できるか（要実データ検証）。循環路線（始点=終点）の扱いは不明、要検証。

### 5-B. 目的地登録（フェーズ3-B）

**正常系**: 地図タップで最寄りバス停コードが特定され目的地として登録できる。登録済み目的地は一覧表示・削除ができる。

**失敗系**: 地図読み込み失敗時のフォールバック。タップ地点周辺にバス停が存在しない場合のエラー表示。

**エッジケース**: 同一目的地の重複登録、登録件数上限は不明。

### 5-C. 「関連のみ」フィルター実ロジック（フェーズ3-B）

**正常系**: 目的地登録済みの状態でトグルONにすると登録済み目的地を経由する系統のみに絞り込まれる。OFFで全件表示に復帰。

**失敗系**: 目的地未登録時のトグルON挙動は不明（要検討）。BusRoutesキャッシュ未準備時は安全側で全件表示にフォールバック。

**エッジケース**: 複数目的地登録時のOR/AND判定は不明（要検討）。`Direction`判定が取れない系統での誤判定リスク。

## 9. APIの変更

- `GET /api/bus-routes/summary?serviceNo=&direction=`（案）— 指定系統・方向の経路情報（選定済み経由地点、始点・終点）を返す。サーバー側で選定ロジックを完結させ、フロントには整形済みデータを渡す方針を推奨（生データ転送量削減のため）
- `GET /api/destinations/related-services?stopCode=`（案、3-B）— 登録済み目的地を経由する系統判定。目的地データはlocalStorage完結のためリクエストパラメータで渡す設計になる可能性（要検討）
- 目的地登録時の最寄りバス停取得は既存`/api/bus-stops/nearby?limit=1`で代替可能（新規エンドポイント不要の可能性）
- 既存3エンドポイントは変更しない
